# Security audit checklist

Twenty four points. Each line is answered `pass`, `fail`, `not applicable`
with a reason, or `unknown` with the missing input. No line is left blank.

## 1. Authentication

- [ ] Password hashing uses a memory hard algorithm with current parameters.
- [ ] Credentials are compared in constant time.
- [ ] Session or token lifetime is bounded and stated.
- [ ] Session identifier is rotated on login and on privilege change.
- [ ] Logout invalidates server side, not only the cookie.
- [ ] Password reset tokens are single use, short lived and unguessable.
- [ ] A stolen token cannot be replayed after logout or password change.
- [ ] Email change requires re-authentication and confirms both addresses.

## 2. Authorization

- [ ] Every route enforces authorization server side.
- [ ] Every server action enforces it, not only the page that renders it.
- [ ] No control is protected by hiding it in the UI alone.
- [ ] Role checks compare against a closed set, not a free string.
- [ ] Admin routes are enumerated and each one verified.

## 3. Object level authorization

- [ ] Every query taking an identifier from the request is scoped by owner.
- [ ] Every update and delete is scoped, not only the read.
- [ ] Nested resources verify the parent, not only the child.
- [ ] Included relations cannot leak rows the caller may not see.
- [ ] Bulk endpoints verify each element, not the first one.

## 4. Privilege escalation

- [ ] Role, plan, quota and ownership fields cannot be set by the client.
- [ ] Mass assignment is impossible: the write list is explicit.
- [ ] A second route does not offer an unprotected path to the same operation.
- [ ] Invitation and team join flows cannot grant a higher role than the
      inviter holds.

## 5. Injection

- [ ] All SQL is parameterised, including dynamic ordering and filtering.
- [ ] Identifiers used in dynamic SQL come from an allowlist, not from input.
- [ ] Document queries cannot receive operator objects from input.
- [ ] ORM filters are not built by spreading request keys.

## 6. Command injection

- [ ] No shell is invoked with an interpolated string.
- [ ] Process arguments are passed as an array, never concatenated.
- [ ] Binaries invoked on user files receive a server generated path.

## 7. Path traversal

- [ ] Every filesystem path built from input is resolved and asserted inside
      the intended root.
- [ ] Filenames are generated by the server, not taken from the client.
- [ ] Archive extraction rejects entries escaping the destination.

## 8. Cross site scripting

- [ ] Raw HTML sinks are enumerated, each with a sanitiser or a proof the
      content is trusted.
- [ ] Markdown rendering sanitises the output.
- [ ] Attribute and URL interpolation cannot produce a script scheme.
- [ ] User controlled SVG is not served from the application origin.
- [ ] A content security policy limits the damage of a missed sink.

## 9. Server side request forgery

- [ ] URLs from input are restricted by scheme allowlist.
- [ ] Hosts are restricted by allowlist where the feature permits.
- [ ] DNS resolution is checked against private and link local ranges.
- [ ] Redirects are not followed, or are re-validated at each hop.
- [ ] Cloud metadata addresses are unreachable from the request path.

## 10. Deserialisation and evaluation

- [ ] No evaluation of user supplied strings.
- [ ] No dynamic template compilation from input.
- [ ] Object merges reject prototype polluting keys.
- [ ] Deserialisation formats that can instantiate arbitrary types are unused.

## 11. File uploads

- [ ] Content type sniffed from bytes, not from the header or extension.
- [ ] Size limit enforced by the server, before buffering the whole file.
- [ ] Storage name generated by the server.
- [ ] Storage location is not executable and not inside the web root.
- [ ] Served content type is set explicitly, with no sniffing.
- [ ] Images are re-encoded where the product allows it.

## 12. Cross site request forgery

- [ ] State changing requests authenticated by cookies carry a token or rely
      on a verified same site policy.
- [ ] The protection is verified in practice, not assumed from the framework.
- [ ] Login and logout are protected too.

## 13. Cookies

- [ ] HttpOnly on session cookies.
- [ ] Secure in every environment that serves over TLS.
- [ ] SameSite set explicitly.
- [ ] Domain and path scoped as narrowly as the product allows.
- [ ] No sensitive value stored in a readable cookie.

## 14. Security headers

- [ ] Content security policy present and not a wildcard.
- [ ] Strict transport security on TLS origins.
- [ ] Frame ancestors or frame options set.
- [ ] Content type options set to nosniff.
- [ ] Referrer policy set.
- [ ] Headers verified on a real response, not only in the config file.

## 15. CORS

- [ ] Allowed origins are an explicit list.
- [ ] The request origin is not reflected blindly.
- [ ] Credentials are not allowed together with a permissive origin.
- [ ] Preflight handling does not bypass authorization.

## 16. Sensitive data exposure

- [ ] Responses are built from an explicit field list.
- [ ] Password hashes, tokens and internal identifiers never serialise.
- [ ] Included relations are filtered.
- [ ] Production errors are generic; stack traces stay in the logs.

## 17. Secrets

- [ ] No secret in tracked files.
- [ ] No secret in the client bundle.
- [ ] No secret in the repository history, checked, not assumed.
- [ ] No token in a URL, where it lands in logs and referrers.
- [ ] Missing secrets cause a startup failure rather than a silent default.

## 18. Logging and privacy

- [ ] Request bodies, headers and cookies are not logged verbatim.
- [ ] Tokens and passwords are redacted at the logger, not at each call site.
- [ ] Personal data collected is limited to what the feature needs.

## 19. Business logic

- [ ] Quantities and amounts reject zero, negative and fractional values where
      they are meaningless.
- [ ] Currency is validated against an allowlist.
- [ ] Discounts cannot stack beyond the stated rule, and cannot exceed the
      total.
- [ ] Refunds cannot exceed the captured amount.
- [ ] State transitions are validated against the current state.
- [ ] Expired resources are rejected at use, not only hidden in the UI.

## 20. Race conditions

- [ ] Single use resources are enforced by a unique constraint or a lock.
- [ ] Balance and quota changes are atomic.
- [ ] Double submission cannot create two effects.
- [ ] Concurrent updates cannot silently overwrite each other.

## 21. Payments

- [ ] The charged amount is computed server side from stored prices.
- [ ] The provider webhook signature is verified before the payload is used.
- [ ] Capture and refund are idempotent.
- [ ] Order state cannot be advanced by a client call.
- [ ] The secret key never reaches the client bundle.

## 22. Webhooks

- [ ] Signature verified against the raw body, before parsing.
- [ ] Timestamp freshness window enforced.
- [ ] Replays rejected by an idempotency record.
- [ ] Failures are not acknowledged as success.
- [ ] Amounts and statuses are re-fetched rather than trusted from the payload
      where the provider allows it.

## 23. Rate limiting

- [ ] Login, reset, signup, invitation and search are limited.
- [ ] Expensive and cost incurring endpoints are limited.
- [ ] The limit works across instances.
- [ ] The limit is keyed on something the attacker cannot rotate freely.

## 24. Enumeration and disclosure

- [ ] Login returns the same message for unknown account and wrong password.
- [ ] Password reset returns the same response whether or not the account
      exists.
- [ ] Signup does not reveal that an address is already registered, or does so
      deliberately with the tradeoff stated.
- [ ] Response timing does not distinguish the two cases in a measurable way.

## Standing checks

- [ ] Dependency audit command run, output read, advisories judged for
      reachability.
- [ ] Container runs as a non root user where a container exists.
- [ ] Debug flags off in production configuration.
- [ ] No default credentials in any configuration file.
- [ ] Storage buckets and database network access are not public by default.
